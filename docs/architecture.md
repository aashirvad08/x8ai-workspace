# Architecture

x8ai Workspace is a terminal-first development environment for macOS. It hosts
existing tools — shells, coding agents, model providers, MCP servers, Git — and
orchestrates them. It does not implement an LLM, and it does not implement a coding
agent. This document describes the architecture Phase 0 establishes and the shape
later phases build into.

Status markers used below: **[built]** exists in the repository today;
**[planned: Phase N]** is designed here but deliberately not implemented yet.

---

## 1. Principles

1. **Host, don't replace.** Claude Code, OpenCode, Codex, Aider and others are
   external programs the user installs. The app gives them a great environment.
2. **No privileged vendor.** Nothing in the architecture is shaped around one agent,
   one model provider or one MCP server. Compatibility is decided by declared
   protocols (§7, §8), not by names.
3. **The native side is trusted; the webview is not.** Anything that touches
   processes, files, secrets or the network happens in Rust behind a narrow,
   explicitly granted command surface (§4, `docs/security.md`).
4. **Declarative first, code where it earns its place.** Integrations are data
   (`crates/core`). Per-tool quirks that data cannot express live in small Rust
   adapters, not in the UI.
5. **Build what the phase needs.** Contracts and boundaries exist now; subsystems
   are implemented in their phase (`docs/roadmap.md`).

## 3. Repository map

| Path | What it is | Rule |
| --- | --- | --- |
| `crates/core/` | `x8ai-core`: IPC contracts and integration definitions | No Tauri, no I/O, no process management. Compiles and tests on any OS. |
| `src-tauri/` | `x8ai-desktop`: the Tauri host | The only crate that depends on Tauri. Thin: wiring, commands, state. |
| `src-tauri/capabilities/` | Which window may call which command | Every grant is explicit and reviewed. |
| `src-tauri/permissions/autogenerated/` | Per-command `allow-*`/`deny-*` permissions generated by `tauri-build` | Committed, so permission changes show in review. CI fails on drift. |
| `src/app/` | Composition root's UI: shell layout, status bar | UI only. No business logic, no Tauri imports. |
| `src/native/` | Typed client for native commands, error normalization | The only frontend module that may import `@tauri-apps/*`. |
| `src/contracts/generated/` | TypeScript types generated from `x8ai-core` | Never edited by hand. Regenerate with `pnpm contracts`. |
| `src/architecture.test.ts` | Tests that enforce the frontend module boundaries | Update deliberately when boundaries change. |
| `docs/decisions/` | Architecture decision records | One per significant decision. |

Subsystem modules are created in the phase that fills them rather than as empty
folders. The planned homes are:

| Concept | Frontend (`src/`) | Native (`crates/` unless noted) | Phase |
| --- | --- | --- | --- |
| core | `native/`, `contracts/` | `core` | 0 [built] |
| terminal | `terminal/` (xterm.js view, session state) | `pty` + session registry in `src-tauri` | 1 |
| workspace | `workspace/` (layout, projects) | `workspace` (roots, trust, scoped fs) | 2 |
| editor | `editor/` | uses `workspace` fs commands | 3, 9 |
| agents | `agents/` (launcher UI) | `agents` (registry, detection, runtime) | 4 |
| models | `models/` (provider settings UI) | `providers`, `secrets` | 5, 6 |
| mcp | `mcp/` | `mcp` | 7 |
| git | `git/` | `git` | 8 |
| catalog | `catalog/` | `catalog` | 10, 11 |

Frontend dependency direction: `app/` → feature modules → `native/` and
`contracts/`. Nothing depends on `app/` except `main.tsx`, and nothing outside
`native/` imports Tauri. `src/architecture.test.ts` enforces both rules.

Native dependency direction: `src-tauri` → feature crates → `x8ai-core`. Feature
crates never depend on Tauri, which keeps them testable without a webview and
reusable from a future CLI or headless test harness.

## 4. Frontend/native boundary [built]

The webview renders UI and holds view state. The native host owns everything with
side effects. They communicate only through Tauri IPC.

**Mechanisms**

| Mechanism | Direction | Use | Status |
| --- | --- | --- | --- |
| Commands (`invoke`) | webview → native → reply | Request/response: queries, actions | [built] `get_app_info` |
| Channels (`tauri::ipc::Channel`) | native → webview, ordered stream | High-throughput streams: PTY output, agent output, logs | [planned: Phase 1] |
| Events | native → webview, broadcast | Low-rate notifications: session exited, file changed | [planned: as needed] |

**Contracts.** Every type that crosses IPC is defined once in `x8ai-core` with serde
and exported to TypeScript with `ts-rs` (ADR 0003). The generated files are
committed. CI regenerates them and fails if they differ from the committed copy.

**Errors.** Commands return `Result<T, CommandError>`, serialized as
`{ code, message }` with `code ∈ invalidInput | notFound | permissionDenied |
internal`. The frontend's `NativeError` adds `ipc` for calls that never reached a
command: not registered, not granted, bad arguments, or no Tauri bridge. Errors
are shown to the user. They are never swallowed.

**Grants.** `src-tauri/build.rs` declares every app command, which makes Tauri
generate `allow-*` and `deny-*` permissions with no default grant. A command runs
only if a capability in `src-tauri/capabilities/` grants it to the calling window.
Otherwise Tauri rejects the call before the command's code runs. This was verified by
revoking the grant and observing `Command get_app_info not allowed by ACL`.

### Adding a native command

1. If the command introduces new request or response types, define them in the
   appropriate crate (`x8ai-core` for contracts) with `#[derive(Serialize,
   Deserialize, TS)]` and `#[ts(export)]`. Then run `pnpm contracts`.
2. Implement the command in `src-tauri/src/commands.rs` (or a submodule). Keep it
   thin: validate the untrusted arguments, then call into a crate.
3. Register it in `generate_handler!` in `src-tauri/src/lib.rs`.
4. Add its name to `COMMANDS` in `src-tauri/build.rs`. The next build regenerates
   `src-tauri/permissions/autogenerated/`. Commit that change.
5. Grant `allow-<command-name>` in the narrowest capability that needs it.
6. Add a typed method to `NativeClient` in `src/native/client.ts`, with a test.

## 5. Process model

- **App process (Rust).** One per app instance. It runs the Tauri event loop, owns
  all native state, and is the parent of every child process the app starts.
- **Webview.** WKWebView runs page content in WebKit's own sandboxed helper
  processes. From the app's point of view it is an untrusted client (ADR 0005).
- **Child processes** [planned: Phase 1+]. These include login shells, agents,
  stdio MCP servers, language servers and git. Each is:
  - started only by the native layer, from an explicit program, arguments and
    environment. Nothing is passed through `sh -c`, and the webview never
    supplies a program path.
  - placed in its own process group (session leader for PTYs), so signals reach
    the whole tree and cleanup kills grandchildren too.
  - tracked in a registry with an id, status and exit code, and killed (SIGHUP,
    then SIGKILL after a grace period) when its session closes or the app quits.
    Orphans are a bug.
- **Environment.** A GUI app started from Finder inherits launchd's minimal `PATH`,
  not the user's shell `PATH`. Shells are started as login shells so they read the
  user's profile. Non-shell programs (agents, MCP servers) are resolved against
  the user's login-shell environment, which is captured once per app start
  [planned: Phase 4]. App-held secrets are never placed in the app's own
  environment, so they cannot leak by inheritance.

## 6. Terminal architecture [planned: Phase 1]

The terminal is the substrate for everything interactive, agents included, so it
is designed first. The proposed stack (ADR 0006) is `portable-pty` in Rust,
xterm.js in the webview, and a Tauri Channel carrying output.

```
xterm.js ──keystrokes──▶ invoke terminal_write(id, bytes) ──▶ PTY master ──▶ shell / agent
xterm.js ◀─bytes─ Channel<Vec<u8>> ◀─ reader thread (batching) ◀─ PTY master ◀─┘
resize  ──▶ invoke terminal_resize(id, cols, rows) ──▶ TIOCSWINSZ (child gets SIGWINCH)
```

- **Session** = PTY pair + child process + reader thread + output channel. Sessions
  live in a native registry keyed by `SessionId`, and the webview holds only ids.
  Multiple sessions are the normal case.
- **Input** is raw bytes. Ctrl+C and Ctrl+D are not special-cased: xterm.js emits
  `0x03` and `0x04`, and the PTY line discipline turns them into SIGINT for the
  foreground process group and EOF. This is what makes interactive programs,
  prompts and full-screen TUIs work unmodified.
- **Output** is raw bytes. The native layer does not parse ANSI, and xterm.js
  renders colors, cursor movement and the alternate screen. The reader batches
  reads (by size or time) to keep IPC overhead low under heavy output, and applies
  backpressure instead of buffering without bound.
- **Resize** follows the xterm.js fit. The native layer applies it to the PTY, and
  the kernel delivers SIGWINCH.
- **Lifecycle:** `starting → running → exited(code) | failed(reason)`. Exit is
  reported, scrollback remains readable, and the session is removed explicitly.
- **Environment:** `TERM=xterm-256color`, `COLORTERM=truecolor`, the user's locale,
  and the workspace directory as cwd (Phase 2).
- **Terminal-specific risks** (OSC 52 clipboard writes, OSC 8 links, title
  injection) are handled in xterm.js configuration. See `docs/security.md`.

The interface the rest of the app will depend on, sketched here and finalized in
Phase 1:

```rust
trait SessionHost {
    fn spawn(&self, spec: SessionSpec, output: Channel<Vec<u8>>) -> Result<SessionId>;
    fn write(&self, id: SessionId, bytes: &[u8]) -> Result<()>;
    fn resize(&self, id: SessionId, size: TerminalSize) -> Result<()>;
    fn status(&self, id: SessionId) -> Result<SessionStatus>;
    fn kill(&self, id: SessionId) -> Result<()>;
}
```

## 7. Agent architecture [contracts built; runtime planned: Phase 4]

Every target agent (Claude Code, OpenCode, Codex, Aider) is primarily an
interactive terminal program. So the agent runtime is built on the session
substrate, not beside it:

```
AgentRuntime = AgentDefinition (data) + launch in a Session (Phase 1)
             + per-agent config adapter (model, MCP)          (Phases 5, 7)
```

- **`AgentDefinition`** [built, `crates/core/src/agent.rs`] declares an id, name,
  `LaunchSpec` (program, args, env), requirements (for example "`claude` must be
  on PATH"), and capabilities: which model APIs the agent can use
  (`modelApis`) and which MCP transports it supports (`mcpTransports`).
- **The runtime** [planned: Phase 4] detects installed agents, resolves the
  program to an absolute path, starts it in a session with the workspace as cwd,
  and reports status. It maps directly onto the session interface: start = spawn,
  sendInput = write, resize, getStatus = status, getOutput = channel, stop = kill.
- **Config adapters** [planned: Phases 5 and 7] translate "use provider P with model
  M and MCP servers S" into what each agent actually reads: flags, environment
  variables or a generated config file. This is the one place agent-specific code
  is allowed, isolated per agent behind one trait.
- **Structured mode** [future, after Phase 4]. Some agents also offer machine
  interfaces: headless JSON streams, local servers, and the Agent Client Protocol
  (ACP). A second runtime kind can use these for richer UI (diff review, tool call
  approval) without changing the definition format.

The app never bypasses an agent's own safety model. For example, it does not add
"skip permissions" flags by default (`docs/security.md`).

## 8. Model architecture [contracts built; implementation planned: Phases 5–6]

- **`ModelProviderDefinition`** [built, `crates/core/src/model.rs`] declares
  endpoints, auth and known models. Each endpoint is a (`ProviderApi`, `baseUrl`)
  pair. The APIs are wire protocols: `anthropicMessages`,
  `openAiChatCompletions`, `openAiResponses` and `gemini`.
- **Compatibility is protocol matching.** An agent can use a provider if they share
  a `ProviderApi`. For example, Ollama serves both OpenAI-compatible and
  Anthropic-compatible endpoints, so the same local model can serve Claude Code,
  OpenCode and Aider. The fixture tests in `crates/core/tests/` demonstrate this.
- **The app does not proxy model traffic** in the initial design. Agents talk to
  providers directly. The app's job is to store credentials (Keychain), test
  connectivity, list models, and inject configuration into agents at launch.
  A local gateway that translates between protocols is a possible later addition.
  It would get its own ADR, because it would put the app on the data path of
  every prompt.
- **Local models** [planned: Phase 6]: detect Ollama and other local servers, list
  and pull models, and treat "runs on this machine" as first-class information,
  since it means code never leaves the device.
- **Credentials** are referenced by `SecretName` only (§10).

## 9. MCP architecture [contracts built; implementation planned: Phase 7]

- **`McpServerDefinition`** [built, `crates/core/src/mcp.rs`] declares a transport:
  `stdio` (a `LaunchSpec`, the same type agents use) or `streamableHttp` (a URL),
  plus requirements.
- **The agent is the MCP client.** For each agent session, the app selects the
  workspace's enabled servers that match the agent's `mcpTransports`, and its config
  adapter writes them into the agent's configuration.
- **The app as MCP client** [planned: Phase 7], for inspection only: start a server
  in a controlled way, run the `initialize` handshake, and list its tools so the
  user can see what they are enabling.
- **MCP gateway** [deferred, needs an ADR]. Routing agent↔server traffic through
  the app would enable central policy and audit, at the cost of latency and
  complexity. It is not decided yet.
- Remote-server authentication (OAuth per the MCP specification) is designed in
  Phase 7. Header-token shortcuts are deliberately not modelled yet.

## 10. Secrets [planned: Phase 5]

Definitions can reference secrets only by `SecretName` (for example `EnvValue::Secret`
or `ProviderAuth::ApiKey`). They can never contain values. The native secret store
(macOS Keychain) resolves a secret at the moment a specific process is launched and
places it only in that process's environment. Secret values never cross IPC to the
webview, never appear in logs or error messages, and are never stored in files the
app writes. Validation rejects URLs with embedded credentials and API-key traffic
over plain HTTP to non-loopback hosts. Both rules are built and tested.

## 11. Catalog architecture [planned: Phases 10–11]

The catalog distributes `IntegrationDefinition`s [built,
`crates/core/src/definition.rs`], a tagged union of agent, model provider and MCP
server definitions. Skills and templates become variants once their schemas exist.

- **Sources:** built-in (bundled and reviewed), remote index (signed and
  versioned), and user-defined (local and untrusted by default).
- **An entry** adds metadata around a definition: version, source, integrity
  (checksums or signatures), homepage and license.
- **Install and connect** means: check requirements, show the exact commands and
  secrets involved, run the installer only after explicit approval, then register
  the definition. For already-installed tools like Claude Code this is "Connect",
  meaning detect and register.
- **Trust** is recorded per definition and pinned by content hash. If a definition
  changes after approval, approval is required again.
- Definitions reject unknown fields (`deny_unknown_fields`), so a manifest cannot
  silently carry settings this version does not understand. A `schemaVersion`
  arrives with the catalog format.

## 12. Security boundaries

Summarized here and detailed in `docs/security.md`:

| Boundary | Enforced by | Status |
| --- | --- | --- |
| Webview → native | Tauri capabilities (explicit per-command grants), strict CSP, frozen prototypes, no shell/fs plugins | [built] |
| Native → child process | Explicit `LaunchSpec`, no shell interpolation, user approval, per-process secret injection | [planned: Phases 1, 4, 7] |
| Workspace boundary for the app's own file operations | Canonicalized paths under the workspace root | [planned: Phase 2] |
| Integration trust | Source, pinned hash, re-approval on change | [planned: Phase 10] |
| Inside a child process | **Not enforced.** Children run with user privileges. OS-level sandboxing is future work. | — |

## 13. Extension strategy

1. **New agent, provider or MCP server:** add a definition (data). No code changes
   if its protocols are already known.
2. **New agent with unusual configuration:** add a config adapter in the agents
   crate, implementing one trait.
3. **New wire protocol or transport:** add an enum variant in `x8ai-core`. Tests and
   the generated TypeScript make every consumer handle it.
4. **No in-process plugins.** Third-party code is not loaded into the app process or
   the webview. Integrations run as separate processes. If in-process
   extensibility is ever needed, a sandboxed runtime such as WebAssembly would be
   evaluated in its own ADR.
